Solana's average daily transaction throughput has nearly doubled, and the full-chain feed can now spike to 1.3–1.8 Gbps. If you're experiencing Dragon's Mouth gRPC disconnects, WebSocket instability, or stale streams, the root cause is almost always a client-side environment that hasn't kept pace with current chain throughput. Work through the checklist and issue guides below before contacting support — most problems resolve at this step.

## Connection requirements checklist

Before diving into specific issues, verify your environment meets the minimum requirements for reliable streaming.

<AccordionGroup>
  <Accordion title="Network bandwidth: 5 Gbps recommended">
    The full-chain feed can spike above 1 Gbps during congestion. **5 Gbps of network capacity** is strongly recommended for large or full-chain subscriptions.

    In cloud environments, instance types are often capped at 1 Gbps by default. Check your instance's network cap in your cloud provider's console — this is a common cause of disconnects on otherwise healthy setups.
  </Accordion>

  <Accordion title="Round-trip latency: ≤ 50 ms to the Triton endpoint">
    Lower latency gives you more headroom during network variability spikes. Measure it from the same machine that runs your subscriber client:

    ```bash
    ping your-endpoint.mainnet.rpcpool.com
    ```

    Latency above 50 ms will make it harder to stay on the tip of the chain during throughput spikes.
  </Accordion>

  <Accordion title="zstd compression is enabled">
    Without compression, bandwidth requirements increase significantly. Enabling zstd compression makes it much easier to stay on the chain tip during throughput spikes.

    Pass `--compression zstd` in your client configuration or set the equivalent option in your SDK.
  </Accordion>

  <Accordion title="Adaptive window size is enabled">
    Set `http2-adaptive-window` to `true`. This allows the gRPC client to adjust HTTP/2 flow-control window sizes automatically based on throughput, preventing the client from being bottlenecked by fixed window constraints.
  </Accordion>

  <Accordion title="Not running in a cloud Lambda or serverless function">
    Cloud Lambda environments (AWS Lambda and equivalents) do not work with persistent streaming connections. They can leave many open connections on the server side, degrading service for all clients. Use a persistent compute environment (a container, VM, or dedicated server) for gRPC streaming.
  </Accordion>

  <Accordion title="Not using vanilla Node.js for high-throughput gRPC">
    Vanilla Node.js is too slow for high-throughput Solana gRPC streams. Use one of the following instead:

    - **Rust** — recommended for lowest latency and highest throughput
    - **Go** — well-supported and performant
    - **TypeScript/Node.js via the Yellowstone gRPC client** — use the purpose-built client library described on the [gRPC Subscriptions](/streaming/dragons-mouth-grpc) page, not a generic Node.js gRPC library

    The specialized TypeScript client handles the performance constraints that vanilla Node.js cannot.
  </Accordion>
</AccordionGroup>

## Test your stream capacity

Before investigating specific symptoms, run the benchmark client to confirm your environment can keep up with current chain throughput:

```bash
./client-ubuntu-22.04 \
  --http2-adaptive-window true \
  --compression zstd \
  --endpoint http://aaa.mainnet.rpcpool.com \
  --x-token <your-token> \
  subscribe --transactions --accounts --stats
```

A healthy setup outputs a ping message every 10 seconds with a total bandwidth between 60–80 Mbps. If you see this, your environment is keeping up with the chain tip and disconnections should not occur. If the benchmark drops or lags, address the requirements in the checklist above before proceeding.

The `client-ubuntu` tool is described on the [gRPC Subscriptions](/streaming/dragons-mouth-grpc) page.

## Common issues and fixes

<AccordionGroup>
  <Accordion title="Stream disconnects frequently">
    Frequent disconnections almost always indicate the client cannot process data fast enough — the server-side stream is fine, but the client is applying back pressure.

    Work through this sequence:

    1. Verify your instance has at least 5 Gbps of network capacity
    2. Confirm round-trip latency to the endpoint is ≤ 50 ms
    3. Enable zstd compression and adaptive window size
    4. Run the benchmark client to measure actual throughput
    5. If you're using Node.js, switch to the specialized Yellowstone TypeScript client or a Rust/Go implementation
    6. If you're running in a Lambda or serverless function, migrate to a persistent compute environment

    If you've confirmed all of the above and disconnections continue, contact support with your benchmark output and the instance type you're running on.
  </Accordion>

  <Accordion title="Not receiving expected updates">
    If your stream is connected but you're not seeing the data you expect:

    - Verify your subscription filters match the accounts, programs, or transaction signatures you're watching
    - Check that your subscription is not being filtered out by commitment level — Dragon's Mouth delivers data at `processed` commitment by default
    - Confirm you haven't accidentally subscribed to an empty filter (an empty filter on some fields means "match nothing", not "match everything" — check the filter semantics in the [gRPC Subscriptions](/streaming/dragons-mouth-grpc) docs)
    - If you're watching a low-activity account, use a ping subscription alongside your data subscription to confirm the connection is live
  </Accordion>

  <Accordion title="429 errors on gRPC or WebSocket">
    `429 Too Many Requests` (or the gRPC equivalent `RESOURCE_EXHAUSTED`) means you've hit the rate limit for your subscription or connection tier.

    **What to do:**

    1. Pause all requests from the affected IP for **10 seconds** — retrying immediately will not clear the limit
    2. Implement exponential backoff in your reconnection logic
    3. If you're hitting limits consistently, check [customers.triton.one](https://customers.triton.one/) to review your current usage and contact support to request a higher limit
    4. Review whether you're creating multiple subscriptions unnecessarily — consolidate filters into a single subscription where possible

    <Tip>
      Shared pool WebSocket connections are capped. If you need more than the standard subscription count, you need a dedicated node.
    </Tip>
  </Accordion>

  <Accordion title="Stream goes stale — no new updates">
    A stale stream means the connection is open but you're no longer receiving updates that should be arriving. This is different from a disconnection.

    **Diagnose staleness:**

    - Check the `slot` field in incoming messages. Compare it to a `getSlot` call against the same or a secondary RPC endpoint. If the stream's slot value is significantly behind the chain tip, the stream is stale.
    - Dedicated node users can check the "Tracking Tip" folder in their Grafana dashboard for slot latency relative to the network.

    **Common causes:**

    - Client-side back pressure: your application is processing messages too slowly, and the server is waiting for the client to consume the buffer
    - Bandwidth saturation: the host's network is at capacity and TCP buffers are filling up
    - Underlying connection issues that didn't trigger a clean disconnect

    If staleness is caused by back pressure, profile your message processing pipeline. Move heavy processing off the hot path of the stream consumer and use a queue to decouple ingestion from processing.
  </Accordion>

  <Accordion title="'Too many requests' on subscribe">
    If you receive a rejection when attempting to subscribe:

    - Check how many active subscriptions you currently have; shared pools have a maximum subscription count
    - Close subscriptions you're no longer using before opening new ones
    - If you're running multiple clients, consolidate subscriptions where possible using filter unions
    - For workloads requiring many simultaneous subscriptions, contact support about dedicated node options
  </Accordion>

  <Accordion title="Reconnection loses position — messages missed during downtime">
    Dragon's Mouth delivers data at the time of subscription. If your client disconnects, you will miss any updates that occurred while it was offline — there is no automatic replay.

    **To reconnect without missing data:**

    - Record the last `slot` value you received before the disconnect
    - On reconnect, pass `from_slot` in your subscription request to resume from that point
    - For workloads where guaranteed delivery and no data loss are more important than lowest latency — such as accounting, analytics, indexing, or compliance — consider using **Fumarole** instead of raw Dragon's Mouth gRPC. Fumarole provides persistent streaming with automatic redundancy and a 23-hour cache, so missed data is recoverable after reconnection.

    See the [Fumarole](/streaming/fumarole) documentation for details.
  </Accordion>
</AccordionGroup>

## Web3.js socket connection issues (Node.js)

If you're running high-throughput applications using `@solana/web3.js` in a Node.js environment, you may encounter persistent socket and connection errors under heavy concurrent load.

### Common error messages

These errors are a strong indicator that your application is hitting local system limits for network connections:

```
cause: ConnectTimeoutError: Connect Timeout Error
code: 'UND_ERR_CONNECT_TIMEOUT'
```

```
cause: Error: connect ECONNREFUSED 1.2.3.4:443
code: 'ECONNREFUSED'
```

```
cause: Error: Client network socket disconnected before secure TLS connection was established
code: 'ECONNRESET'
```

```
cause: SocketError: other side closed
code: 'UND_ERR_SOCKET'
```

### Root cause: port exhaustion

These errors are not caused by the RPC node or the `@solana/web3.js` library. They are caused by Node.js's `fetch` implementation, which uses the `undici` HTTP client. By default, `undici` opens a new TCP socket for each outgoing request. Under heavy concurrent load, this exhausts the available ephemeral ports on your operating system.

**Diagnose port exhaustion** on a UNIX-based system:

```bash
lsof -i -n -P | grep node | awk '{print $9}' | awk -F '->' '{print $1}' | \
  awk -F ':' '{print $2}' | sort -u | wc -l
```

A count in the thousands is a clear sign of this issue.

### Solutions

<AccordionGroup>
  <Accordion title="Option 1: Limit connections with a global agent (recommended)">
    Configure Node.js to use a global connection pool with `undici`. This forces the HTTP client to reuse connections rather than opening a new socket for every request.

    Install `undici` and set the global dispatcher at the very beginning of your application's entry point:

    ```typescript
    import { Agent, setGlobalDispatcher } from 'undici';

    setGlobalDispatcher(
      new Agent({
        connections: 50, // start with 50; increase if consistently at capacity
      })
    );
    ```

    Start with a limit of 50 connections. Monitor your port usage with the `lsof` command. If all 50 connections are consistently in use and your application needs more throughput, increase the limit gradually.

    <Tip>
      Reusing connections also makes your application faster. Each new TCP connection requires a TLS handshake, which adds latency. A pool of 50 persistent connections will outperform an unlimited pool of short-lived ones.
    </Tip>
  </Accordion>

  <Accordion title="Option 2: Use axios with a custom HTTPS agent">
    If you prefer `axios`, create a client with a dedicated `https.Agent`. The `@solana/web3.js` `Connection` object accepts a custom fetch implementation.

    A full working example is available at [this Gist](https://gist.github.com/WilfredAlmeida/9adea27abb5958178c4370c5656e89b7).
  </Accordion>

  <Accordion title="Option 3: Switch to the Bun runtime">
    [Bun](https://bun.sh/) is a modern alternative to Node.js. Its internal HTTP client handles connection pooling more efficiently and does not exhibit the socket exhaustion issue. This is a straightforward option for new projects, though it may require changes for existing codebases.
  </Accordion>

  <Accordion title="Option 4: Use the new @solana/web3.js v2">
    Anza Labs is developing a new version of the `@solana/web3.js` library (currently in technical preview) that uses `undici` internally and shows fewer of these errors. With the global dispatcher configuration from Option 1 applied, remaining errors should resolve.

    Note: the new library is not API-compatible with the current version — migrating requires a ground-up rewrite of any code that uses the library.
  </Accordion>

  <Accordion title="Other SDKs with the same issue">
    SDKs such as `jito-ts`, which uses `node-fetch` internally, can produce `ERR_STREAM_PREMATURE_CLOSE` errors with the same underlying cause. You can fix this by providing an `http(s).Agent` configuration to limit the number of connections. The same connection-pooling approach applies regardless of which underlying HTTP library is in use.
  </Accordion>
</AccordionGroup>

## Best practices for stable streaming

<CardGroup cols={2}>
  <Card title="Reconnect with backoff" icon="rotate">
    Always implement exponential backoff in your reconnect logic. Immediately reconnecting after a disconnect causes thundering-herd problems and may result in 429 errors that block your reconnect further.
  </Card>
  <Card title="Resume from a slot" icon="bookmark">
    Record the last slot you received. On reconnect, pass `from_slot` in your Dragon's Mouth subscription to pick up where you left off without missing updates.
  </Card>
  <Card title="Keep connections alive" icon="heart-pulse">
    Send WebSocket ping frames at least every 60 seconds. Many load balancers and network devices silently close idle connections. Regular pings prevent this.
  </Card>
  <Card title="Monitor with stats flags" icon="chart-bar">
    Pass `--stats` in your gRPC client to monitor stream health. Watch the slot field in incoming messages to detect staleness before it causes problems in your application.
  </Card>
</CardGroup>

## Choosing the right streaming product

<Note>
  Dragon's Mouth prioritizes lowest latency over absolute data completeness. If your workload prioritizes guaranteed delivery — such as accounting, analytics, indexing, or compliance — use **Fumarole** instead. Fumarole provides persistent streaming with 23-hour caching and automatic redundancy.
</Note>

| Workload | Recommended product |
| --- | --- |
| Trading, market-making, arbitrage | Dragon's Mouth gRPC |
| Frontend / browser apps | Whirligig WebSockets |
| Indexing, accounting, analytics | Fumarole |
| Decoded JSON instead of raw binary | Vixen (parser on top of Dragon's Mouth) |
