Yellowstone Shield lets you control which validators are allowed to process your Solana transactions. You create an on-chain policy — either an allowlist of validators you trust, or a blocklist of validators you want to exclude — and then attach that policy's address to your transactions when you send them. The Cascade-enabled RPC checks each potential forwarding target against your policy and only routes your transaction to validators that meet your criteria.

This protects you from validators that engage in sandwich attacks, frontrunning, or other practices that extract value from users at the protocol level.

## How it works

<Steps>
  <Step title="Create a policy">
    Deploy an on-chain policy specifying your strategy (allow or deny) and the list of validator identities it covers. When you create a policy, you receive a special SPL token (via Token Extensions) that gives you management rights.
  </Step>
  <Step title="Note your policy address">
    After creation, save the mint address (policy PDA). Anyone who knows this address can use the policy. Only wallets holding the management token can modify it.
  </Step>
  <Step title="Attach the policy to your transactions">
    Include the policy address when calling `sendTransaction`, either as a request parameter or an HTTP header. The RPC filters validators against your policy before forwarding.
  </Step>
  <Step title="Maintain the policy over time">
    New validators join Solana every epoch. Review and update your policy regularly to keep it effective.
  </Step>
</Steps>

<Warning>
  Shield only works with RPCs that support it — including Triton One endpoints using Cascade (Yellowstone Jet). Standard Solana RPCs ignore the `forwardingPolicies` parameter entirely.
</Warning>

## Quick start: attaching a policy to your transactions

If you already have a policy address (your own or a community-maintained one), you can start using it immediately. There are two ways to pass a policy to your RPC.

<Tabs>
  <Tab title="RPC method parameter">
    Include `forwardingPolicies` in the `sendTransaction` options object:

    ```json
    {
      "jsonrpc": "2.0",
      "id": 1,
      "method": "sendTransaction",
      "params": [
        "<base64_encoded_transaction>",
        {
          "encoding": "base64",
          "skipPreflight": true,
          "forwardingPolicies": ["<your_policy_pda>"]
        }
      ]
    }
    ```
  </Tab>
  <Tab title="HTTP header">
    Pass one or more comma-separated policy addresses in the `Solana-ForwardingPolicies` header:

    ```http
    POST /your-token HTTP/1.1
    Host: your-endpoint.mainnet.rpcpool.com
    Content-Type: application/json
    Solana-ForwardingPolicies: "<policy_pda_1>,<policy_pda_2>"
    ```

    This is useful when you don't control the JSON-RPC call directly, for example when using a library that wraps `sendTransaction` internally.
  </Tab>
</Tabs>

### JavaScript example

Standard `@solana/web3.js` does not expose `forwardingPolicies`, so you need to construct the JSON-RPC call directly:

```typescript
import { Transaction } from "@solana/web3.js";
import bs58 from "bs58";

const transaction = new Transaction().add(/* your instructions */);
const signedTx = await wallet.signTransaction(transaction);
const serializedTx = bs58.encode(signedTx.serialize());

const response = await fetch("https://your-endpoint.mainnet.rpcpool.com/your-token", {
  method: "POST",
  headers: {
    "Content-Type": "application/json",
  },
  body: JSON.stringify({
    jsonrpc: "2.0",
    id: 1,
    method: "sendTransaction",
    params: [
      serializedTx,
      {
        encoding: "base58",
        skipPreflight: true,
        forwardingPolicies: ["<policy_pda>"],
      },
    ],
  }),
});

const result = await response.json();
const signature = result.result;
```

## Understanding policies and tokens

When you create a Shield policy, an SPL token is minted using the Token Extensions program. You receive one token in your wallet, and that token represents management authority over the policy:

- Anyone holding the token can add, remove, or update validator identities in the policy.
- You retain the mint authority, so you can mint additional tokens to share management with other team members.
- The policy itself lives on-chain and can be used by anyone who knows its address — you don't need to grant permission for others to reference it in their transactions.
- If you transfer all your tokens without retaining one, you lose the ability to modify the policy.

## Finding existing policies

The [Yellowstone Shield policy explorer](https://www.validators.app/yellowstone-shield) lists all known policies on mainnet. For each policy you can see:

- The strategy (allowlist or blocklist)
- The current validator list
- When the policy was last updated

You can copy any policy address directly from the explorer and use it in your transactions without creating your own policy.

**Common policy types include:**

- Blocklists of validators known for sandwich attacks and frontrunning
- Allowlists of high-performing or geographically distributed validators
- Community-curated blocklists maintained by active researchers

## Creating your own policy

### Prerequisites

- Solana CLI installed and configured
- A wallet with SOL for transaction fees
- A list of validator vote account identities

### Step 1: Install the Shield CLI

```bash
git clone https://github.com/rpcpool/yellowstone-shield
cd yellowstone-shield
cargo build --release --bin yellowstone-shield-cli
```

### Step 2: Prepare policy metadata

Create a JSON file describing your policy and host it on IPFS or Arweave:

```json
{
  "name": "My Validator Policy",
  "symbol": "MVP",
  "description": "Blocks validators known for sandwich attacks",
  "image": "https://your-image-url.com/image.png",
  "external_url": "https://your-website.com",
  "attributes": []
}
```

### Step 3: Create the policy

```bash
# Blocklist: deny these validators
yellowstone-shield-cli policy create \
  --strategy deny \
  --name "My Validator Policy" \
  --symbol "MVP" \
  --uri "https://your-metadata-url.json"

# Allowlist: only allow these validators
yellowstone-shield-cli policy create \
  --strategy allow \
  --name "My Validator Policy" \
  --symbol "MVP" \
  --uri "https://your-metadata-url.json"
```

The CLI outputs your policy's mint address. Save it — you'll need it when sending transactions.

### Step 4: Add validators

Create a text file with one validator identity address per line:

```text
ValidatorIdentity1...
ValidatorIdentity2...
ValidatorIdentity3...
```

Then add them to your policy:

```bash
yellowstone-shield-cli identities add \
  --mint <your_mint_address> \
  --identities-path validators.txt
```

### Step 5: View and manage your policy

```bash
# View current policy details and validator list
yellowstone-shield-cli policy show --mint <mint_address>

# Replace the entire validator list
yellowstone-shield-cli identities update \
  --mint <mint_address> \
  --identities-path new_validators.txt

# Remove specific validators
yellowstone-shield-cli identities remove \
  --mint <mint_address> \
  --identities-path validators_to_remove.txt
```

## Important limitations

<Warning>
  Shield is a filter, not a guarantee. Understanding its limitations is critical before relying on it for time-sensitive operations.
</Warning>

**Policies need active maintenance.** New validators appear every epoch, and validators that engage in harmful behaviour can be newly registered at any time. Your policy only blocks validators on your list — validators that aren't listed yet have no restriction. Regularly review and update your policy to remain effective.

**Dropped transactions, not queued.** If the current leader or candidate validators don't meet your policy criteria, the transaction is dropped. Shield does not hold or queue transactions for later delivery. For time-critical operations like arbitrage or liquidations, a strict policy could cause your transaction to miss its window.

**Only works with compatible RPCs.** The `forwardingPolicies` parameter is a Triton One / Yellowstone Jet extension. Standard Solana RPCs silently ignore it.
